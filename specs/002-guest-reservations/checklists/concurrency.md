## No-Overlap Invariant (table and guest email)

- [ ] CHK001 Is the overlap rule (half-open ranges on instants) stated once and referenced identically by the table invariant, the guest-duplicate rule, the availability lookup and the database claim filter? [Consistency, Spec §Edge Cases, Spec §FR-011, Spec §FR-026, Research R4]
- [ ] CHK002 Does the spec define "a reservation" for invariant purposes the same way the plan does? FR-001/FR-005/FR-026 speak of "existing/confirmed reservations", while the plan decides availability and duplicates from claimed `TableDay`/`GuestDay` intervals, which also include in-flight and orphaned claims. [Conflict, Spec §FR-001, Spec §FR-026, Research R5–R6]
- [ ] CHK003 Is FR-011's clause "MUST hold even if the application checks are bypassed by concurrent timing" written so it can be checked objectively, e.g. as "the stored state never contains two overlapping intervals for one table, whatever the request interleaving"? [Measurability, Spec §FR-011]
- [ ] CHK004 Is the per-email invariant (FR-026) stated with the same strength as FR-011, i.e. enforced at the database level and holding when application checks are bypassed, or is the weaker wording intentional? [Consistency, Spec §FR-026 vs §FR-011]
- [ ] CHK005 Is it documented that keying `TableDay`/`GuestDay` by start date is safe only because a reservation never crosses midnight, and is the "one accepted edge" referenced in R5/R3 shown not to break either invariant? [Assumption, Research R3, Research R5, Spec §Assumptions]
- [ ] CHK006 Is there a requirement that the unique indexes on `{ tableId, date }` and `{ email, date }` exist before the first write, and that startup fails if they cannot be built? Without them the upsert can create two calendar documents for one key and the invariant breaks silently. [Gap, Data Model §TableDay, Data Model §GuestDay]
- [ ] CHK007 Is the database-level guarantee stated to hold across several application processes and instances, not only within one process, and is that deployment assumption written down? [Assumption, Research R5]

## Claim, Release and Retry Design

- [ ] CHK008 Are all outcomes of `claimInterval` specified and mapped to caller behavior: claimed, overlap, `11000` then claimed on retry, `11000` then overlap on retry, and any other database error? [Completeness, Data Model §Interval claim operations]
- [ ] CHK009 Is it specified that an infrastructure error during a claim (not `11000`) must surface as `INTERNAL_ERROR` and never be reported as `duplicate_reservation` or `no_table_free`? [Gap, Exception Flow, Research R6 steps 6–7]
- [ ] CHK010 Is the reasoning that one retry without upsert always settles the `11000` case written down, including the precondition that calendar documents are never deleted? Is it stated that a second `11000` or other error on the retry is an internal error? [Clarity, Research R5]
- [ ] CHK011 Is the required behavior specified when `releaseInterval` itself fails on a failure path (for example the database is down)? Is the result, an orphan interval, acknowledged as a second source of orphans besides a process crash? [Gap, Recovery, Research R5, Research R6 step 8]
- [ ] CHK012 Is the order in which intervals are released on each failure path specified (table before guest, or the reverse), and does the spec say which outcome is visible to concurrent requests while the release is in progress? [Clarity, Research R6]
- [ ] CHK013 Does "releases on every failure path" (plan, decision 5) come with a list of every failure point in steps 5–8, e.g. an error after the guest claim and before any table claim, an error during the re-read, an error during a table release, so that none is left unspecified? [Completeness, Plan §Key Design Decisions, Research R6]
- [ ] CHK014 Is behavior specified when the `Reservation` insert has an **unknown outcome**, e.g. a timeout or connection loss after the server may have written the document? Releasing both intervals in that case could leave a stored reservation with no claimed interval and allow a double booking. [Gap, Exception Flow, Research R6 step 8, Data Model §Consistency between collections]
- [ ] CHK015 Is it specified that `releaseInterval` removes only the interval with the caller's own `reservationId`, and never another request's interval? [Clarity, Data Model §Interval claim operations]

## Reserve Flow Order of Operations

- [ ] CHK016 Is the full order (normalize → convert time → duplicate pre-read → availability snapshot → generate id → claim guest → claim tables in candidate order with re-check → insert → confirm) stated consistently in spec Edge Cases, plan Constraints, research R6 and the contract Check order? [Consistency, Spec §Edge Cases, Plan §Technical Context, Research R6, Contract §Check order]
- [ ] CHK017 Is the precedence rule "a request that is both duplicate and unavailable reports duplicate" defined for concurrent requests too? Under the R6 design, a same-email request whose pre-read misses an in-flight guest claim, and which is also unavailable, reports `no_table_free` instead of `duplicate_reservation`. [Ambiguity, Spec §Edge Cases, Research R6 steps 3–6]
- [ ] CHK018 Does the spec state whether the post-claim re-check covers only table state (not removed, capacity) or also closed date and schedule? As planned, a closed date added between the snapshot and the insert does not stop the reservation, which may conflict with FR-021 ("always reflect the current configuration"). [Gap, Conflict, Spec §FR-021, Research R6 step 7]
- [ ] CHK019 Is the reason for claiming the guest interval before the table intervals written down as a requirement-level property (a duplicate request never holds a table even briefly), not only as a rejected alternative? [Traceability, Research R6 Alternatives]
- [ ] CHK020 Is the fallback to the next candidate required to keep FR-010's ordering, i.e. after losing the smallest suitable table the request takes the next table in the defined order? Is falling back to a table that was not in the snapshot (freed in the meantime) explicitly allowed or excluded? [Clarity, Spec §FR-010, Research R9]
- [ ] CHK021 Is the case "the snapshot reports available but every candidate claim fails" explicitly mapped to `NO_AVAILABILITY / no_table_free`, with the guest interval released first? [Completeness, Research R6 step 7]
- [ ] CHK022 Does FR-014/FR-026's "MUST store nothing" specify whether temporary interval claims count as stored, and what final state is required, e.g. "no `Reservation` and no interval with that `reservationId` remains"? [Clarity, Spec §FR-014, Spec §FR-026]

## Table Removal vs. Reservation Race

- [ ] CHK023 Is the spec's removal condition ("at least one reservation that has not yet ended", FR-017) consistent with the plan's condition ("a claimed interval ending after now", R10)? Orphan and in-flight intervals also block removal under the plan; is that accepted in the spec? [Conflict, Spec §FR-017, Research R10, Contract §DELETE /tables/{id}]
- [ ] CHK024 Is the visible effect of R10 step 1 specified? Between "set removed" and "revert", concurrent lookups and reservations treat the table as removed and may get `party_too_large` or `no_table_free` even though the removal is then refused. Does the spec accept that, given FR-017's "leave the table unchanged"? [Gap, Conflict, Spec §FR-017, Spec §FR-019, Research R10]
- [ ] CHK025 Are the "spurious" outcomes of the race (staff get a 409 although no reservation ends up on the table, and a customer is refused although the table stays active) stated as acceptable in the spec, not only in research R10? [Gap, Spec §US4, Research R10]
- [ ] CHK026 Is a rollback requirement defined for when the revert in R10 step 3 fails or the process crashes before it? In that case the table stays removed while upcoming reservations reference it, which breaks FR-017. [Gap, Recovery, Research R10]
- [ ] CHK027 Is the boundary of "has not yet ended" defined for an interval whose end equals the removal instant, consistently with the `end > now` condition in the plan? [Clarity, Edge Case, Spec §FR-017, Research R10]
- [ ] CHK028 Is the capacity-reduction race (a `PATCH /tables/{id}` lowering capacity between a reservation's re-read and its insert) addressed? As designed, the affected-reservation report reads `Reservation` documents and would miss the reservation that is still in flight. [Gap, Spec §FR-022, Research R11]
- [ ] CHK029 Is SC-008's "list exactly the affected reservations" scoped for changes made concurrently with reservations, e.g. as eventually or best-effort accurate, or is exactness required under concurrency too? [Ambiguity, Spec §SC-008, Spec §FR-022]

## Orphan Intervals and Crash Recovery

- [ ] CHK030 Is the orphan-interval risk stated in the spec (it currently appears only in the plan, research R5 and data-model)? The spec's Edge Case "no partial reservation remains" is absolute and contradicts the documented crash window. [Conflict, Spec §Edge Cases, Plan §Complexity Tracking, Research R5]
- [ ] CHK031 Is the safety direction of an orphan documented as a requirement, i.e. an orphan can only cause false "not available" or duplicate answers and never a double booking? [Clarity, Data Model §Consistency between collections]
- [ ] CHK032 Are the customer-visible effects of orphans specified? An orphan `GuestDay` interval makes every later overlapping attempt by that email fail with `duplicate_reservation` although no reservation exists; an orphan `TableDay` interval hides the table and blocks its removal. [Gap, Spec §FR-026, Spec §FR-017]
- [ ] CHK033 Is "removed by hand" backed by a defined way to identify an orphan (an interval whose `reservationId` has no `Reservation`) and a documented manual procedure, so that the known debt can be acted on? [Gap, Recovery, Research R5, Plan §Phase Ordering 7]
- [ ] CHK034 Does the plan's Constitution Check still pass with the orphan risk? Principle III requires integrity at the database level. Is the claim "no overlap is ever violated, only availability is lost" stated where the gate decision is recorded? [Consistency, Plan §Constitution Check, Constitution §III]

## Customer-Visible Outcomes When a Claim Loses a Race

- [ ] CHK035 Is the response for each losing path listed in one place: lost guest claim → `409 CONFLICT / duplicate_reservation`; all table claims lost → `409 NO_AVAILABILITY / no_table_free`; re-read finds the table removed or too small and no candidate is left → `no_table_free`; insert failure → `500 INTERNAL_ERROR`? [Completeness, Contract §POST /reservations, Research R6]
- [ ] CHK036 Is it specified that a request can be refused as a duplicate because of a concurrent same-email request that **later fails**? In that case the customer is told they already hold a reservation that never comes to exist. [Gap, Spec §US2-8, Research R6 step 6]
- [ ] CHK037 Is the customer-facing contract for retries defined? There is no idempotency key, so a retry after a lost response to a successful request is refused as a duplicate, and the secret code (returned only once, FR-013) cannot be recovered. Is that outcome accepted in the spec? [Gap, Spec §FR-013, Spec §FR-026, Spec §US2-9]
- [ ] CHK038 Is it specified what a customer who got `500 INTERNAL_ERROR` should expect when retrying, given that a release failure can leave an orphan and the retry would then get `duplicate_reservation`? [Gap, Exception Flow, Spec §Edge Cases]
- [ ] CHK039 Does the contract say whether the `duplicate_reservation` conflict reveals anything about the existing reservation (time, table), and is that consistent with keeping guest data private on public operations? [Clarity, Contract §New error code]
- [ ] CHK040 Is the snapshot nature of availability (spec Edge Case: an available time may be taken before reserving) reflected in a defined, stable message or code that tells the client a retry with another time is appropriate? [Clarity, Spec §Edge Cases, Spec §FR-014]

## Acceptance Criteria & Testability of Concurrency Requirements

- [ ] CHK041 Are SC-002 and US2-4 written so they cannot pass without real contention? For example: do they require evidence that requests actually interleaved at the database, or a forced interleaving such as the pause hook in R10, rather than relying on `Promise.all` alone? [Measurability, Spec §SC-002, Research R14]
- [ ] CHK042 Do the concurrency acceptance criteria cover the same-email race (US2-8), candidate fallback, the removal race in both orderings, and the insert-failure path, each with the expected final database state (no overlapping intervals, no orphans, no reservation on a removed table), not only response codes? [Coverage, Spec §US2, Spec §US4, Research R14]
