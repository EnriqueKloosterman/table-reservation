# Data Model: Availability Lookup and Guest Reservations

**Feature**: `002-guest-reservations` | **Date**: 2026-11-07 | **Plan**: [plan.md](./plan.md)

Feature 001 entities (`StaffMember`, `Table`, `WeeklySchedule`, `ClosedDate`) are unchanged
in shape; see [001 data model](../001-restaurant-setup/data-model.md). This feature adds
three collections. Every new model is wrapped in `registerModel()` so `initModels()` builds
its indexes (the unique ones must exist before the first write).

Conventions (constitution III): instants are UTC `Date`s; restaurant-local values are text
(`"YYYY-MM-DD"`, `"HH:mm"`) interpreted in `RESTAURANT_TIME_ZONE`.

## Reservation (`reservations`)

| Field | Type | Rules |
|---|---|---|
| `_id` | ObjectId | Generated by the service *before* claiming intervals, so intervals can reference it. |
| `status` | String | Enum `["confirmed"]`, default `"confirmed"`. Other states arrive with cancellation. |
| `tableId` | ObjectId → `Table` | Required. Kept when the table is later soft-deleted (FR-018). |
| `date` | String | Restaurant-local start date `YYYY-MM-DD`. |
| `startTime` | String | Local `HH:mm` snapshot as requested. |
| `endTime` | String | Local `HH:mm` snapshot of `endAt` (may differ from wall-clock arithmetic on DST days, [R3](./research.md#r3-containment-end-time-and-dst-days)). |
| `startAt` | Date (UTC) | `localToUtc(date, startTime)`. |
| `endAt` | Date (UTC) | `startAt + RESERVATION_DURATION_MINUTES`. |
| `partySize` | Number | Integer 1–50. |
| `guestName` | String | Trimmed, 1–100. |
| `guestEmail` | String | Trimmed + lowercased, ≤ 254. |
| `guestPhone` | String | Trimmed, 7–20 chars. |
| `secretCodeHash` | String | SHA-256 hex of the secret code. `select: false`; never serialized. |
| `createdAt` | Date (UTC) | Set from the injected clock (`timestamps` off; the service writes it, so tests pin it). |

**Indexes**

- `{ tableId: 1, endAt: 1 }` — capacity-reduction report (FR-022) by table.
- `{ endAt: 1 }` — upcoming reservations for the schedule report.
- `{ date: 1 }` — closed-date report.

There is **no** overlap index here: the overlap invariant lives in `TableDay`.

**Lifecycle**: created once in `confirmed`; never modified by configuration changes
(FR-020). No update or delete path exists in this feature.

## TableDay (`tabledays`)

The per-table, per-date calendar that enforces FR-011 atomically.

| Field | Type | Rules |
|---|---|---|
| `tableId` | ObjectId → `Table` | Required. |
| `date` | String | `YYYY-MM-DD` (the reservation's start date). |
| `intervals` | Array of `{ reservationId: ObjectId, start: Date, end: Date }` | Pairwise non-overlapping (half-open) — guaranteed by the claim filter, not by a schema validator. `_id: false` on items. |

**Indexes**: `{ tableId: 1, date: 1 }` **unique**. The `tableId` prefix also serves the
removal check `{ tableId, "intervals.end": { $gt: now } }`.

## GuestDay (`guestdays`)

The per-email, per-date calendar that enforces FR-026 atomically.

| Field | Type | Rules |
|---|---|---|
| `email` | String | Normalized guest email. |
| `date` | String | `YYYY-MM-DD`. |
| `intervals` | Same shape as `TableDay.intervals` | Pairwise non-overlapping. |

**Indexes**: `{ email: 1, date: 1 }` **unique**.

## Interval claim operations (`reservations/interval-claims.ts`)

```text
claimInterval(model, key, { reservationId, start, end }) → Promise<boolean>
  filter  = { ...key, intervals: { $not: { $elemMatch: { start: { $lt: end }, end: { $gt: start } } } } }
  update  = { $push: { intervals: { reservationId, start, end } } }
  try updateOne(filter, update, { upsert: true }) → true
  on 11000: updateOne(filter, update) → matchedCount === 1   (retry once, no upsert)
  any other error (also on the retry) → rethrown, never mapped to "overlap"

releaseInterval(model, key, reservationId) → Promise<void>
  updateOne(key, { $pull: { intervals: { reservationId } } })   // only the caller's own interval
```

Calendar documents are never deleted, which is why one retry suffices. `initModels()` must
await the unique indexes of `TableDay` and `GuestDay`; startup fails if they cannot be built.

`key` is `{ tableId, date }` or `{ email, date }`. Single-document atomicity makes the
filter check and the push indivisible ([research R5](./research.md#r5-enforcing-no-two-overlapping-reservations-per-table-without-transactions)).

## Consistency between collections

| Invariant | How it holds |
|---|---|
| A table never holds two overlapping reservations | Atomic claim on `TableDay`. |
| An email never holds two overlapping reservations | Atomic claim on `GuestDay`, claimed before any table. |
| Every `Reservation` has its interval in its `TableDay` and `GuestDay` | Claims precede the insert; a definite insert failure releases both; an unknown insert outcome is resolved by an existence check first and keeps the intervals if it cannot be resolved (R6 step 8). |
| No reservation ends on a removed table | Reserve flow re-reads the table after claiming; removal pre-checks `TableDay` claims, sets `removed`, re-checks and reverts on conflict ([R10](./research.md#r10-table-removal-vs-reservation-race-fr-017)). |
| No stored reservation contradicts the closed dates, schedule or table capacity current when the request finished | Post-store verification with rollback (R6 step 9), together with the affected report computed after the staff change (R11). |
| **Not guaranteed**: every interval has a `Reservation` | Orphan intervals: process stop between claim and insert/release, a failed release, or intervals kept after an unresolvable insert outcome. Safe direction: they only hide a time, never allow an overlap. Manual identification and cleanup documented in the README (FR-031, [R5](./research.md#r5-enforcing-no-two-overlapping-reservations-per-table-without-transactions)). |

### `src/modules/availability/availability.domain.ts`

```text
type Reason = "too_soon" | "too_far_ahead" | "closed_date" | "closed_day"
            | "outside_service_hours" | "party_too_large" | "no_table_free"

type Rules = { timeZone, durationMinutes, slotIntervalMinutes, minNoticeMinutes, horizonDays }
type TableInfo = { id: string, name: string, capacity: number }       // non-removed only
type Interval = { start: Date, end: Date }

type DaySnapshot = {
  now: Date, rules: Rules, date: string,
  periods: ServicePeriod[],            // the weekday's periods, sorted
  isClosedDate: boolean,
  tables: TableInfo[],
  intervalsByTable: Map<string, Interval[]>   // from TableDay of that date
}

checkAvailability(snapshot, { time, partySize })
  → { available: true, tables: TableInfo[] }        // ordered candidates (chooseTables)
  | { available: false, reason: Reason }

listBookableTimes(snapshot, { partySize })
  → { periods: [{ name, times: string[] }], reason?: Reason }   // reason iff periods empty

chooseTables(tables, partySize, intervalsByTable, range) → TableInfo[]
  // capacity ≥ partySize and no overlapping interval;
  // sorted by capacity, then name (Intl.Collator "en", numeric, base sensitivity)
```

The `tables` field of an available answer is internal (used by the reserve flow) and is
never serialized; `GET /availability` returns only the yes/no and reason (FR-007).

**Reason precedence** ([R7](./research.md#r7-reason-precedence)):
`checkAvailability`: too_soon → too_far_ahead → closed_date → closed_day →
outside_service_hours → party_too_large → no_table_free.
`listBookableTimes` (FR-008): too_soon (date < today) → too_far_ahead → closed_date →
closed_day → party_too_large → outside_service_hours → too_soon (notice) → no_table_free.

**Grid**: for each period, `t = start, start + interval, …` while
`toMinutes(t) + duration ≤ toMinutes(end)`. A grid time is listed iff
`checkAvailability(snapshot, { time: t, partySize })` is available (this is literally how
the list is computed, which makes the SC-004 invariant hold by construction; the unit test
still checks it independently).

## Validation rules (from the spec)

| Input | Rule | Error |
|---|---|---|
| `date` | Real calendar date `YYYY-MM-DD` | 400 `VALIDATION_ERROR` |
| `time` | `HH:mm`, 00:00–23:59 | 400 |
| `partySize` (query) | String `^[1-9][0-9]?$`, value ≤ 50; one occurrence | 400 |
| `partySize` (body) | JSON integer 1–50 | 400 |
| `name` | 1–100 chars after trim | 400 |
| `email` | Valid format, ≤ 254 after trim; stored lowercased | 400 |
| `phone` | After trim, 7–20 chars of digits, spaces, `-`, `(`, `)`, optional leading `+`; ≥ 7 digits | 400 |
| unknown query parameter / body field | refused | 400 |
| party larger than every non-removed table | business rule, not validation | lookups: 200 with `reason: "party_too_large"`; reserve: 409 `NO_AVAILABILITY` |
